# Run OpenCode beside z/OS, not on it

A z/OS systems programmer can use OpenCode productively today, but only as a **workstation-side agent that drives the mainframe remotely**. It runs on macOS, Linux or Windows/WSL, talks to an approved (ideally internal) model endpoint, and reaches z/OS through Zowe CLI, an MCP server, or plain SSH to USS. It cannot run on z/OS USS or on Linux on IBM Z, because neither OpenCode nor its Bun runtime ships s390x or z/OS builds. The work it does well is read-and-explain: explaining inherited JCL, REXX and CLISTs; drafting JCL, REXX and Ansible for human review; summarising job output and syslog; diffing exported PARMLIB members; writing runbooks. The work it does badly, or should not be allowed to do, is acting on production: console commands, SMP/E APPLY/ACCEPT, RACF changes, PARMLIB activation, APF/LNKLST updates, deletes. Its defaults are permissive, with most tools set to `allow`, and its conversation-sharing feature can upload whole sessions to a public link. So a site has to impose guardrails before the first session. Lock the configuration through OpenCode's managed `/etc/opencode/` layer. Give the agent a dedicated low-privilege RACF ID, which is the real security boundary. Start read-only against a sandbox LPAR. Route every change through existing change control. The ecosystem is young: the official Zowe MCP server is "early stage" and not yet on public npm, and no published benchmark measures LLM accuracy on JCL, SMP/E or RACF syntax. Treat everything here as a pilot pattern, not settled practice.

## OpenCode is a fast-moving MIT agent with two incompatible major versions

OpenCode is "an open source AI coding agent" with terminal (TUI), desktop and IDE front ends ([OpenCode docs](https://opencode.ai/docs)). It is MIT-licensed and hosted at `anomalyco/opencode`, formerly `sst/opencode`. At the time of research the repo had **about 215k GitHub stars** ([GitHub](https://github.com/sst/opencode)). Release cadence is the first thing a regulated shop has to plan around. **V1 shipped 1.19.1, 1.19.2 and 1.19.3 within two days in mid-October 2026** ([GitHub releases](https://github.com/anomalyco/opencode/releases)). Meanwhile, a re-architected **V2 (npm `@opencode/cli`) appeared on 11 September 2026 and reached 2.0.28 within a month** ([capitalandcompute.net](https://capitalandcompute.net/blog/opencode-2-0-what-changed/)). The two lines share the `opencode` command, cannot be installed side by side, and differ in config schema, permission syntax, plugin API, server API and LSP behaviour ([V2 migration guide](https://opencode.ai/v2/docs/migrate-v1/)). V1.19.2 pins V1 users to 1.x: the curl installer refuses to install 2.x. Homebrew Core's `opencode` formula, on the other hand, now tracks V2 ([GitHub releases](https://github.com/anomalyco/opencode/releases)), so the package manager you pick quietly decides which major version you get.

My recommendation for a sysprog pilot in October 2026 is **V1 (1.19.x)**. It is the default install, its documentation is complete, and it still runs language servers. V2 parses `lsp` config but **runs no language servers**, breaks V1 plugins, and **flips `external_directory` from `ask` to `allow` by default** ([V2 migration guide](https://opencode.ai/v2/docs/migrate-v1/)). That silent loosening matters when the agent's working directory sits next to a `zowe.config.json` or SSH keys. No source labels V2 as stable.

Installation is conventional. V1 installs via `curl -fsSL https://opencode.ai/install | bash`, `npm i -g opencode-ai`, `brew install anomalyco/tap/opencode`, Chocolatey/Scoop/mise on Windows (WSL is advised), or a container at `ghcr.io/anomalyco/opencode` ([OpenCode docs](https://opencode.ai/docs)). The platform limit is hard. V2's published binaries cover **only macOS, Windows and Linux on x64 and ARM64** ([V2 docs](https://opencode.ai/v2/docs/)). Bun, the JavaScript runtime OpenCode is built on, likewise lists no s390x, ppc64le or big-endian target ([Bun installation docs](https://bun.sh/docs/installation)). Running under qemu emulation is not a reliable escape hatch either: Bun binaries have crashed under ppc64le emulation in a comparable product ([claudeissues.com](https://claudeissues.com/issue/26332-feature-support-for-ppc64le-in-the-ssh-connector)). The practical topology is the sysprog's laptop or an x86/ARM Linux jump host, with z/OS reached over the network. Older RHEL 7/8 jump hosts work: Bun runs on kernels as old as 3.10 ([Bun installation docs](https://bun.sh/docs/installation)), and "baseline" x64 builds exist for CPUs without AVX.

## Configure it as a locked-down client of your internal model gateway

OpenCode is provider-agnostic. It is built on the Vercel AI SDK and supports **"75+" providers plus any OpenAI-compatible endpoint**. IBM watsonx is not among the built-ins ([Providers docs](https://opencode.ai/docs/providers/)). That makes on-prem and air-gapped use straightforward. Define a custom provider in `opencode.json` with `npm: "@ai-sdk/openai-compatible"` and `options.baseURL` pointing at your vLLM, Ollama or LLM gateway. A watsonx.ai deployment works too, provided a proxy such as LiteLLM fronts it with an OpenAI-compatible API (an inference: no native watsonx provider was found). Local servers have documented defaults: Ollama at `localhost:11434/v1`, LM Studio at `127.0.0.1:1234/v1`, llama.cpp at `127.0.0.1:8080/v1`. The docs warn that you need models with strong tool calling, and that Ollama's `num_ctx` may need raising to 16k–32k before tool calls work ([Providers docs](https://opencode.ai/docs/providers/)). Expect a real quality gap between small local models and frontier models on agentic tasks.

The control plane for a site rollout is OpenCode's **layered config**. Layers merge from remote `.well-known/opencode` org defaults, through user and project `opencode.json` and `.opencode/` directories, up to **managed files in `/etc/opencode/` (Linux), `/Library/Application Support/opencode/` (macOS) or `%ProgramData%\opencode` (Windows), which users cannot override** ([Config docs](https://opencode.ai/docs/config/)). `enabled_providers` acts as an allowlist, and the Enterprise page describes central config that "ensures users reach only your internal AI gateway" ([Enterprise docs](https://opencode.ai/docs/enterprise/)). Corporate networks are handled through `HTTPS_PROXY`/`NO_PROXY`; set `NO_PROXY=localhost,127.0.0.1` so the TUI can reach its own local server. Custom CAs go in via `NODE_EXTRA_CA_CERTS`. For NTLM/Kerberos proxies, the docs suggest an LLM gateway instead ([Network docs](https://opencode.ai/docs/network/)).

Data egress needs a deliberate review. OpenCode states that it "does not store your code or context data": prompts go straight from the workstation to the configured provider ([Enterprise docs](https://opencode.ai/docs/enterprise/)). Several features still reach outward, though. **V1's share feature publishes full conversation history, diffs and tool-use records to a public link**. It defaults to `manual` and is turned off with `"share": "disabled"` ([Mintlify mirror of share docs](https://www.mintlify.com/anomalyco/opencode/share)). On top of that come the auto-update check, the models.dev catalog fetch, LSP auto-downloads, npm plugin installs, and web search and fetch. Each has a documented switch: `OPENCODE_DISABLE_AUTOUPDATE` / `autoupdate: false`, `OPENCODE_DISABLE_MODELS_FETCH` (or a custom `OPENCODE_MODELS_URL`), `OPENCODE_DISABLE_LSP_DOWNLOAD`, `OPENCODE_DISABLE_DEFAULT_PLUGINS` / `--pure`, and permission denies on `webfetch`/`websearch` ([CLI docs](https://opencode.ai/docs/cli/)). OpenCode also reads Claude Code's `CLAUDE.md` and `~/.claude/skills/` as fallbacks unless `OPENCODE_DISABLE_CLAUDE_CODE*` is set ([Rules docs](https://opencode.ai/docs/rules/)), so instructions written for another tool can leak into OpenCode sessions. One gap is unresolved. **No documented telemetry switch exists, and no source states whether the CLI sends usage data to Anomaly.** The privacy policy covers hosted services and the website, not the self-run CLI ([Privacy policy](https://opencode.ai/legal/privacy-policy)). A regulated site should settle the question with a packet capture before approval. Provider credentials sit in plain files (`~/.local/share/opencode/auth.json`, `mcp-auth.json`), so set their file permissions accordingly ([Providers docs](https://opencode.ai/docs/providers/)).

Site knowledge belongs in `AGENTS.md`, the project rules file that `/init` generates and the team commits ([Rules docs](https://opencode.ai/docs/rules/)). For a sysprog repo it should state HLQ conventions, JCL standards, the site CCSID, LRECL and column 73–80 rules, which LPARs are off-limits, and the requirement that SMP/E work stops at APPLY CHECK. Custom slash commands are Markdown files in `.opencode/commands/`. They support `$ARGUMENTS` and `` !`shell` `` output injection ([Commands docs](https://opencode.ai/docs/commands/)), which makes them a clean way to package repeatable read-only workflows, such as "pull this job's spool and explain the abend".

## Three bridges reach z/OS, and Zowe is the backbone of all of them

| Bridge | What the mainframe needs | Agent-friendliness | Maturity / caveats |
|---|---|---|---|
| **Zowe CLI via OpenCode's `bash` tool** | z/OSMF REST for most groups; SSH only for `zos-ssh` | Global `--rfj` JSON output; credentials in OS keyring via team config | v3.x LTS, most mature; Node startup latency per call |
| **Zowe MCP server** (stdio, `type: "local"`) | SSH login + writable USS dir (zowex native server), z/OS 2.5+ | Structured tools with built-in risk tiers and untrusted-data marking | Official but "early stage"; Node 22+, tarball install, not on public npm |
| **IBM RSE API 1.2.5 MCP** (`type: "remote"`) | RSE API with `RSEAPI_MCP_ENABLE=true` | Server-side, zero client install | Requires IDzEE or ADFz VU licence |
| **IBM Z Open Editor / IDz on VS Code MCP** | Zowe profile; DBB/RSE for build tools | ~62 tools incl. DBB, Wazi Deploy | Only live while a VS Code/Bob window hosts it |
| **Plain `ssh` to USS / curl to z/OSMF / Ansible** | OpenSSH + OMVS segment; or z/OSMF; or ZOAU + Python | Universal, but raw text and manual CSRF/encoding handling | Ansible `ibm_zos_core` 2.1.0 gives idempotent, check-mode-capable changes |

**Zowe CLI is the lowest-friction start.** Its core groups map onto sysprog work. `zos-files` handles data sets and VSAM. `zos-jobs` submits jobs and reads spool. `zos-tso` runs TSO commands and REXX. `zos-console` issues console commands through an extended MCS console, and the docs say security administrators should control which commands are allowed. `zos-logs` reads operlog, and `zos-ssh` runs USS commands ([Zowe core command groups](https://docs.zowe.org/stable/user-guide/cli-using-understanding-core-command-groups)). Every command accepts the global `--response-format-json` / `--rfj` flag ([zowe-cli Constants.ts](https://raw.githubusercontent.com/zowe/zowe-cli/master/packages/imperative/src/constants/src/Constants.ts)), which hands the agent parseable output in place of screen-scraped text. Team config (`zowe.config.json`, with secrets stored through `zowe config secure`) is shared with Zowe Explorer when the folder is opened as a VS Code workspace ([Zowe team profiles](https://docs.zowe.org/stable/user-guide/cli-using-using-team-profiles)). The human and the agent therefore work against identical profiles. Zowe 3.5 added environment-variable references in team config and a guarantee that secure values are never logged ([OMP: Zowe 3.5](https://openmainframeproject.org/blog/whats-new-in-zowe-3-5/)). Both help keep passwords out of the agent's context. Note the calendar: **Zowe V3 enters maintenance on 1 March 2027, and V2 support ends 30 March 2027** ([Zowe team profiles](https://docs.zowe.org/stable/user-guide/cli-using-using-team-profiles)).

**The Zowe MCP server is the best structural fit once it matures.** It exposes data set, USS, job, TSO and console tools over SSH via Zowe Remote SSH (zowex). It defaults to a **`read-strict` capability tier, escalating through `read`, `update`, `delete` and `full`**. It applies pattern-based block/elicit/allow gates to TSO and USS commands and marks tool output as untrusted data to blunt prompt injection. A mock mode supports CI runs with no mainframe ([github.com/zowe/zowe-mcp](https://github.com/zowe/zowe-mcp)). The catch is maturity. The server is **not on public npm**, has no tagged releases and about 20 stars, and needs Node 22+. It authenticates by SSH key, then password env var, then Vault; ssh-agent is not supported yet ([zowe-mcp](https://github.com/zowe/zowe-mcp)). Its lead, IBM's Joe Winchester, calls it early stage and is still asking sysprogs where guardrails belong ([OMP blog](https://openmainframeproject.org/blog/using-zowe-in-an-ai-world-with-mcp-agents/)). In OpenCode it slots under `mcp.<name>` as `type: "local"` with a `command` array and credentials passed via `{env:...}`. HTTP servers such as RSE API's `/rseapi/mcp` endpoint use `type: "remote"` with an `Authorization` header ([OpenCode MCP docs](https://opencode.ai/docs/mcp-servers/), [IBM Community: RSE API 1.2.5](https://community.ibm.com/community/user/blogs/dave-mcknight1/2026/06/19/rse-api-125)). MCP tool names carry a server prefix, so `"tools": {"zowe*": false}` can disable them globally and an agent definition can re-enable them for a single agent ([OpenCode MCP docs](https://opencode.ai/docs/mcp-servers/)). Several community z/OSMF, FTP and Endevor MCP servers also exist. One of them is bundled with a pentest tool ([glama](https://glama.ai/mcp/servers/yzc1b7oe5f)), so treat them all as unaudited code holding mainframe credentials.

Two lower-level details decide whether agent edits survive contact with z/OS. The first is **code pages and record formats**. USS auto-converts untagged files only when `_BPXK_AUTOCVT=ON`, and then only between IBM-1047 and ISO8859-1 ([IBM LE file tagging](https://www.ibm.com/support/knowledgecenter/en/SSLTBW_2.1.0/com.ibm.zos.v2r1.ceea300/filtag.htm)). Git on z/OS fails outright when file tags and `.gitattributes` `zos-working-tree-encoding` disagree ([ZOSOpenTools/gitport](https://github.com/ZOSOpenTools/gitport)). Zowe's `--binary`, `--record` and `--encoding` download modes exist precisely to avoid silent conversion of packed, binary or VB data ([Zowe CLI strings](https://raw.githubusercontent.com/zowe/zowe-cli/master/packages/cli/src/zosfiles/-strings-/en.ts)). The agent's `AGENTS.md` should require an explicit encoding on every transfer, a DCB attribute check before any write, and preservation of columns 73–80. The second is **language intelligence**. OpenCode's 34 built-in language servers include none for COBOL, PL/I, HLASM, REXX or JCL, and LSP is off by default ([LSP docs](https://opencode.ai/docs/lsp/)). The open Eclipse Che4z COBOL and HLASM servers are LSP-compatible ([che-che4z-lsp-for-cobol](https://github.com/eclipse/che-che4z-lsp-for-cobol), [code4z](https://github.com/BroadcomMFD/code4z/pull/18/files)), but no source confirms they run standalone over stdio outside VS Code. Wiring them in through OpenCode's custom `lsp` entries is an experiment, not a recipe, and it works only on V1.

## The good tasks read and draft; the bad tasks act on production

The documented AI use cases for sysprogs cluster almost entirely on the read side. IBM's watsonx Code Assistant for Z added JCL explanation aimed explicitly at "veteran sysprogs encountering unfamiliar utilities" ([IBM Community](https://community.ibm.com/community/user/blogs/rich-larin/2024/08/12/wca4z-jcl-explanation)). A SHARE 2024 session showed an assistant explaining JCL and converting it to an Ansible playbook so early-tenure sysprogs could work more independently ([SHARE proceedings](https://www.share.org/Events/Past-Events/Proceedings/Proceeding-Details/using-generative-ai-to-help-modernize-system-programmers-tasks)). The GSUK 2026 Zowe MCP demo listed data sets, viewed members, submitted jobs and issued TSO/console commands. Its use-case discussion covered onboarding, overnight job-failure triage, explaining legacy JCL/COBOL, and audit Q&A on system state ([OMP blog](https://openmainframeproject.org/blog/using-zowe-in-an-ai-world-with-mcp-agents/)). Practitioner trust follows the same line. In BMC's 2026 survey of more than 1,300 mainframe respondents, **40% would let AI suggest code-management actions but only 23% would let it complete them alone; for database reorganisation the split is 43% to 21%** ([SD Times](https://sdtimes.com/mainframe/2026-annual-bmc-survey/)).

| Good fits (low blast radius, human verifies output) | Poor or dangerous fits (keep human-executed) |
|---|---|
| Explaining inherited JCL, REXX, CLIST, COBOL and utility control statements | Console commands on production LPARs |
| Drafting JCL, REXX, Ansible playbooks and z/OSMF workflow XML for review | SMP/E APPLY/ACCEPT without human ++HOLD review |
| Summarising spool, syslog/operlog and abend output (job-failure triage) | RACF/ACF2/TSS changes (PERMIT, ALTUSER, SETROPTS) |
| Diffing PARMLIB/PROCLIB members pulled to git | PARMLIB activation via SET or IPL; APF/LNKLST/LPA updates |
| Runbooks, onboarding notes and documentation | Data set/catalog deletes, zFS reformat or unmount, job cancels |
| Batch "explain" jobs via `opencode run --format json` | HLASM exits running in supervisor state |

The left column plays to OpenCode's strengths. It is a strong text and code tool working on members pulled into a git repo, and its `opencode run` non-interactive mode, with `--agent`, `-m` and `--format json`, can script nightly summarisation from cron or a CI pipeline ([CLI docs](https://opencode.ai/docs/cli/)). The read-and-summarise pattern plausibly extends to Health Checker output, IPL logs and SMF/RMF reports, but no source documents those uses. The right column is dangerous because LLM errors are **fluent and syntactically valid**: a plausible but wrong JCL parameter passes every parser and surfaces only at runtime ([Coralogix](https://coralogix.com/ai-blog/llm-hallucinations/)). Expect invented PARMLIB keywords, operands from the wrong z/OS release, wrong SPACE or DCB values, and REXX that runs on ooRexx but not TSO/E. These failure modes are inferred, not reported. **No citable practitioner reports of specific LLM errors in sysprog work, and no accuracy benchmarks for JCL, SMP/E or RACF syntax, were found.** Their absence argues for caution, not comfort.

The steelman for going further is real. IBM's own watsonx Assistant for Z now offers agentic multi-agent workflows that act "with minimal supervision" over OMEGAMON, System Automation and the workload scheduler ([IBM announcement](https://www.ibm.com/new/announcements/ibm-watsonx-assistant-for-z-bringing-intelligence-and-automation-to-mainframe-it-management-with-agentic-ai), [IBM Community](https://community.ibm.com/community/user/blogs/wolfgang-schberle1/2025/10/24/system-insights-agents-in-wxa4z)), and it can run inference on the Spyre accelerator so data stays on IBM Z ([IBM](https://www.ibm.com/new/announcements/watsonx-assistant-for-z-now-powered-by-spyre-accelerator)). Those actions, however, run as curated "trusted automation" that authorised users trigger, not free-form shell commands. The sensible division of labour is OpenCode as the sysprog's workstation tool for reading, drafting and reviewing, with a governed, catalogued automation channel (Ansible or wxA4Z skills) for anything that changes the system.

## Guardrails must live in RACF, not just in opencode.json

OpenCode's permission system is useful but not a security boundary. V1 rules are `allow`/`ask`/`deny` per tool. `bash` matches parsed commands with `*`/`?` globs, and **the last matching rule wins**. Most tools default to `allow`; only `doom_loop` and `external_directory` default to `ask`, and `*.env` reads are denied ([Permissions docs](https://opencode.ai/docs/permissions/)). The **Build** agent has every tool, while **Plan** defaults edits and bash to `ask` ([Agents docs](https://opencode.ai/docs/agents/)). The `--auto` flag approves every `ask` but still honours `deny` ([CLI docs](https://opencode.ai/docs/cli/)). That gives the first rule for unattended runs: anything that must never happen has to be an explicit `deny`. An illustrative managed policy, built from documented keys, looks like this:

```jsonc
// /etc/opencode/opencode.json  (V1 syntax; V2 uses an ordered "permissions" array)
{
  "share": "disabled",
  "autoupdate": false,
  "enabled_providers": ["internal-gateway"],
  "permission": {
    "*": "ask",
    "webfetch": "deny",
    "websearch": "deny",
    "external_directory": "deny",
    "bash": {
      "*": "ask",
      "zowe zos-files list *": "allow",
      "zowe zos-jobs view *": "allow",
      "zowe zos-jobs list *": "allow",
      "zowe zos-jobs submit *": "ask",
      "zowe zos-files upload *": "ask",
      "zowe zos-files delete *": "deny",
      "zowe zos-console *": "deny",
      "zowe zos-jobs cancel *": "deny"
    }
  }
}
```

Glob matching on command strings can be bypassed through scripts, aliases, pipelines or a cleverly constructed shell line. The docs do not say whether patterns match inside pipelines or subshells. So the policy reduces accidents; it does not prevent determined misuse. The Zowe MCP maintainers say the same about their own tool: "client hints and confirmation dialogs reduce accidents" while **SAF/RACF, USS ACLs and scheduler exits enforce the real boundaries**, and they recommend a dedicated least-privilege SSH user ([zowe-mcp](https://github.com/zowe/zowe-mcp)). General MCP security guidance agrees that a read-only label "is not the final security boundary" and that sites should test that prohibited writes actually fail ([Techstrong.ai](https://techstrong.ai/features/why-read-only-mcp-is-not-read-only-until-the-database-agrees/)). IBM's own IBM i MCP guidance prescribes a dedicated profile with narrow object authority and no special authorities ([IBM ibmi-mcp security doc](https://glama.ai/mcp/servers/@IBM/ibmi-mcp/blob/bdd94b498101779611bdbd43d33d837897cfed11/docs/agents/security.mdx)). That is the closest published analog, because **no RACF profile template for AI agents has been published**. Translated to z/OS, this report recommends:

- a separate, ideally PROTECTED, agent user ID with no SPECIAL, OPERATIONS or AUDITOR attributes
- READ-only access to PARMLIB, PROCLIB and the SMP/E CSIs
- OPERCMDS permits limited to display commands
- no UPDATE access to APF or LNKLST libraries

The rest of the guardrail stack follows from that foundation. Start against ZD&T, Wazi as a Service or a sandbox LPAR, never production. Have the agent write Ansible playbooks and run `ansible-playbook --check` before a human executes them, since `ibm_zos_core` covers jobs, operator commands, data sets, RACF users and started tasks idempotently ([GitHub ibm_zos_core](https://github.com/ansible-collections/ibm_zos_core)). Promote changes only through git plus a CAB ticket. Keep SMP/E APPLY CHECK and ++HOLD review human. Correlate SMF type 80 and type 30 records for the agent ID with OpenCode session transcripts, which `opencode export --sanitize` can extract ([CLI docs](https://opencode.ai/docs/cli/)). Keep production data set contents, PII and passwords out of any prompt bound for a non-approved endpoint, because **everything the agent reads (SYSOUT, RACF listings, customer records in a data set) goes to the model**. Keep the OpenCode server bound to 127.0.0.1: with `server.mdns` enabled and no hostname set, it binds `0.0.0.0` and advertises itself on the LAN ([Config docs](https://opencode.ai/docs/config/)). Finally, vet or ban npm plugins. They install from npm at startup, and some third-party plugin packs ship their own PostHog analytics ([oh-my-openagent privacy policy](https://raw.githubusercontent.com/code-yeongyu/oh-my-openagent/dev/docs/legal/privacy-policy.md)). Plugins can also strengthen guardrails: a `tool.execute.before` hook can block any command that targets a production host ([Plugins docs](https://opencode.ai/docs/plugins/)).

## Conclusion

The bottleneck for z/OS shops is no longer the agent but the bridge and the identity behind it. OpenCode is fully capable as a reasoning and editing engine, but its value on the mainframe is set almost entirely by Zowe and RACF. Which Zowe surface you expose (read-only CLI commands, a tiered MCP server, or raw SSH) and what the agent's RACF ID can touch determine both the benefit and the blast radius. The most valuable early investments are not in OpenCode at all. They are a well-scoped agent RACF ID, a committed `AGENTS.md` that encodes site conventions LLMs cannot know (HLQs, CCSIDs, column rules, forbidden LPARs), and an Ansible check-mode path that turns agent output into reviewable change records.

Two timing risks deserve a calendar entry. OpenCode's V1-to-V2 split will force a permission-config rewrite, and V2's default of `allow` for `external_directory` silently loosens the sandbox. Zowe V3 enters maintenance in March 2027, just as the Zowe MCP server should be reaching npm. Pilot on V1 and Zowe CLI now, and plan to move the structured work to the Zowe MCP server once it publishes releases. Revisit the "act" column only when sites start publishing evidence (error rates, incident reports, RACF templates) that does not yet exist.
